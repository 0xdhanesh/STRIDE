Worked examples: building real threat models

Step-by-step threat models for a typical web app, a microservices system, an application that takes input, processes it, stores it and retrieves it, and an IVR system integrated with a customer support portal. Each comes with a ready-to-run spec.

The recipe (works for any system)

  1. List the actors. Every person and outside system that touches yours becomes an external interactor.
  2. List the code that runs. Each deployable thing becomes a process. If two things are deployed and secured separately, draw two.
  3. List where data rests. Databases, buckets, queues, caches, logs, recordings: each is a data store.
  4. Draw every data flow, one arrow per direction, named after what it carries. Include the boring ones (logging, monitoring, backups); attackers do.
  5. Draw trust boundaries where control, network or identity changes. Put a vendor on the far side of a boundary.
  6. Set types and properties, then read the high-signal threats first and triage.
  7. Write down assumptions in the model details (“traffic inside the cluster is mutually authenticated”). An unchecked assumption is where most real incidents hide.

Each example below can be built in one command from the spec shown. Run it, open the result in the app, then change it to match your own system.

A normal web app

Use this when: a browser-based product: public pages, logins, a database behind it.

The most common shape: a user, a browser, a public web server, an application, a database, and one outside service (email).

1. Draw it

Trust boundaries (box): User device (the browser is not under your control), Public zone (DMZ), Internal network.

ElementStencil typeWhere / notes
VisitorHuman User (external)The person using the site
BrowserBrowser Client (process)In “User device”: you do not control it
Web serverWeb Server (process)In the public zone: terminates TLS, proxies
Web applicationWeb Application (process)Internal: business logic, sessions
DatabaseSQL Database (store)Internal: accounts and orders
Email providerExternal Web ServiceOutside: sends reset emails
Data flow (from → to)CarriesCrosses
Visitor → Browser, Browser → Web serverClicks, typing, page and API requests (HTTPS)User device → Public zone
Web server → Web application and backForwarded requests, rendered responsesPublic zone → Internal
Web application ↔ DatabaseSQL queries and resultsInside Internal
Web application → Email providerPassword-reset emailsInternal → outside

2. What to look for

STRIDEWhereQuestion to askTypical fix
SBrowser → Web serverCan someone reuse or forge a session? Is login protected against guessing?Strong sessions, MFA, lockout, secure cookies
TBrowser → Web applicationIs every field validated on the server? Can a user change a price or role in the request?Server-side validation, parameterised queries
IWeb application → DatabaseIs the database reachable from anywhere else? Are secrets or personal data logged?Network rules, least-privilege DB account, encryption at rest
DPublic zoneWhat stops one client from flooding login or search?Rate limits, timeouts, caching
EWeb applicationIs authorization checked on the server for every action, not just hidden in the UI?Deny-by-default checks and tests per role
RWeb applicationCan an admin action be traced to a person?Audit log with user, time, action

3. Mistakes to avoid

  • Drawing only “the website” as one oval. Split web server, application and database so boundaries have something to cross.
  • Forgetting the reverse flows (responses, query results). Data leaves on them.
  • Leaving out the email provider and other third parties: they hold your users’ data too.

Microservices

Use this when: several small services behind an API gateway, talking to each other and through a message broker.

The risk moves inside: many internal calls, each a chance for a missing check. Model every service-to-service call.

1. Draw it

Trust boundaries (box): Public edge (gateway), Service cluster, Data tier. Add a boundary per team or per sensitivity (for example around payments) as the system grows.

ElementStencil typeWhere / notes
Customer clientBrowser (external)Web or mobile client
API gatewayWeb Server (process)The only public entry point
Identity serviceWeb Service (process)Issues and validates tokens
Orders / Inventory / Payments serviceWeb Service (process) ×3One process per deployable service
Message brokerGeneric Data StoreQueue or topics: it stores messages
Orders DB, Inventory DBSQL Database (store) ×2One database per service
Payment providerExternal Web ServiceOutside
Data flow (from → to)CarriesCrosses
Customer client ↔ API gatewayAPI requests and responsesInternet → Public edge
API gateway → Identity / OrdersToken validation, order requestsEdge → Cluster
Orders → Inventory, PaymentsReserve stock, charge requestInside Cluster
Orders ↔ Message broker ↔ InventoryOrder eventsInside Cluster
Orders / Inventory → their DBsReads and writesCluster → Data tier
Payments → Payment providerCard chargeCluster → outside

2. What to look for

STRIDEWhereQuestion to askTypical fix
SService → serviceDoes a service verify who is calling it, or does it trust anything inside the network?Mutual TLS, service identities, signed tokens
TMessage brokerCan any service publish any event? Are messages validated by the consumer?Per-topic permissions, schema validation
IServices → DBsCan the Orders service read the Inventory database? Do tokens carry more than needed?One credential per service, scoped tokens
DGateway, brokerWhat happens when one service is slow: do callers pile up?Timeouts, circuit breakers, queue limits
EAPI gateway → OrdersIs the end user’s identity passed on and checked again behind the gateway?Re-check authorization in each service
RPaymentsIs each charge traceable end to end?Correlation ids, immutable audit trail

3. Mistakes to avoid

  • Assuming “inside the cluster” means trusted. Draw the flows and ask who authenticates them.
  • One diagram for 40 services. Make one diagram per business flow (checkout, signup) and reuse the element names.
  • Forgetting the broker is a data store: it holds data and needs access control and retention rules.

A complex application: input → process → store → retrieve

Use this when: the app accepts content or data from users, processes it (parsing, scanning, converting, enriching), stores it, and later retrieves it for the same or other users.

Examples: document upload, claims intake, media processing, form builders, data import. The core idea: everything that arrives is hostile until proven otherwise, and everything stored may later be shown to someone else.

1. Draw it

Trust boundaries (box): Public (uploaders and readers), Application and processing, Data tier. If processing runs with different privileges, split it into its own zone in the real system and separate credentials.

ElementStencil typeWhere / notes
Uploader, ReaderHuman User (external) ×2Often different roles
PortalWeb Application (process)Upload form, search, downloads
Upload APIWeb Service (process)Validates and routes
Malware scannerGeneric ProcessScans before anything else touches the file
Job queueCache (store)Work waiting to be processed
Processing workerWin32 Service (process)Parses and extracts: the riskiest code
Object storageCloud Storage (store)The files
Metadata DBSQL Database (store)Extracted data
Search indexNon Relational Database (store)Searchable copy
Data flow (from → to)CarriesCrosses
Uploader → Portal → Upload APIFile and metadataPublic → Application
Upload API ↔ Malware scannerFile to scan, verdictInside Application
Upload API → Job queue → WorkerProcessing job, job and file referenceInside Application
Worker → Object storage / Metadata DB / Search indexProcessed file, extracted data, index entriesApplication → Data tier
Reader → Portal → Upload API → storesSearch, download, lookups, fetch filePublic → Application → Data tier
Portal → ReaderResults and filesApplication → Public

2. What to look for

STRIDEWhereQuestion to askTypical fix
TUploader → Upload APIIs file type checked by content, not name? Size, count and nesting limits? Can a crafted file crash or exploit the parser?Content sniffing, limits, parsers in a sandbox
EWorkerIf the parser is compromised, what can the worker reach? Does it hold keys to every store?Least privilege, separate identity, no network egress
IPortal → ReaderCan one user fetch another user’s file by changing an id? Are stored values escaped when shown (stored XSS)?Per-object authorization, output encoding, signed URLs
TJob queueCan someone put a job on the queue directly? Are jobs idempotent and validated?Authenticated producers, validated payloads
DUpload API, workerCan one huge or malicious file starve everyone else (zip bombs, endless loops)?Quotas, timeouts, per-tenant queues
RUpload APICan you tell who uploaded, who read, who deleted?Audit log of every upload, read and delete
IObject storageIs the bucket public or are links guessable? Are files encrypted and retained longer than needed?Private buckets, expiring signed URLs, retention policy

3. Mistakes to avoid

  • Validating only in the browser. The attacker never uses your form.
  • Treating stored data as trusted when it is read back. It was input once; it is output now: encode it for where it is shown.
  • Giving the processing worker admin rights “for simplicity”.
  • Forgetting derived copies: the search index, caches and thumbnails hold the same sensitive data as the original.

An IVR system integrated into a customer support portal

Use this when: customers phone a company, an automated voice menu (IVR) identifies them and handles simple tasks, and the call can be passed to an agent who works in a support portal backed by customer records.

This mixes telephony and web: voice and keypad input, speech services, one-time codes, card payments, call recording, and an agent desktop. Callers are anonymous and phone numbers can be forged, so never treat the caller as authenticated just because of the number.

1. Draw it

Trust boundaries (box): Contact centre (IVR platform and agent desktop) and Back office and data (portal, records API, customer database, recordings). The carrier, speech service, code provider and payment processor are outside parties, drawn as external interactors. The phone carrier is folded into the call flow; draw it as its own element if you want to model carrier-side threats such as SIP hijacking.

ElementStencil typeWhere / notes
CallerHuman User (external)Anonymous until verified
IVR platformWeb Service (process)Call flow, speech and keypad handling
Speech serviceExternal Web ServiceSpeech-to-text / text-to-speech vendor
One-time-code providerExternal Web ServiceSends SMS or voice codes
Payment processorExternal Web ServiceTakes card details
Agent desktopBrowser Client (process)Screen with caller details
Support agentHuman User (external)Insider: can see customer data
Support portalWeb Application (process)Cases and customer views
Customer records APIWeb Service (process)One front door to customer data
Customer DBSQL Database (store)Personal data
Call recordingsCloud Storage (store)Voice, often with personal data
Data flow (from → to)CarriesCrosses
Caller ↔ IVR platformVoice and keypad tones; prompts and transfer (via the carrier)Phone network → Contact centre
IVR ↔ Speech serviceAudio out, transcript backContact centre → outside
IVR ↔ Customer records APICaller lookup and PIN check, account detailsContact centre → Back office
IVR → One-time-code providerSend one-time codeContact centre → outside
IVR → Payment processorCard payment (keypad entry)Contact centre → outside
IVR → Call recordingsCall recordingContact centre → Back office
IVR → Agent desktop; Agent → Agent desktopCaller details, agent actionsInside Contact centre
Agent desktop → Support portal → Records API → Customer DBCase updates, customer data requests, reads and writesContact centre → Back office
Agent desktop → Call recordingsRecording playbackContact centre → Back office

2. What to look for

STRIDEWhereQuestion to askTypical fix
SCaller → IVRCan the caller ID be faked? Can someone pass “verification” by guessing a PIN or date of birth? Can a cloned voice pass a voice-print check?Do not rely on caller ID; one-time codes; lockout; step-up checks for sensitive actions
SWebhooks / carrier → IVRAre call-event callbacks signed? Can anyone post fake “call ended” events?Verify signatures, allow-list sources
IIVR → Call recordingsDo recordings capture card numbers or one-time codes? Who can replay them? How long are they kept?Pause recording during payment, encrypt, role-limited access, retention limits
IIVR → Payment processorDo card tones ever touch your systems or logs?Send tones straight to the processor (DTMF masking), never store or log them
TCaller → IVRCan spoken or typed input change the call flow, inject into lookups, or break the speech parser?Validate all input, parameterised lookups, limit retries
DCarrier → IVRCan attackers flood the lines or run up costs (toll fraud, premium-rate dialling)?Call rate limits, destination allow-lists, spend alerts
EAgent desktop / portalCan an agent see more than the current caller’s data? Is lookup of any customer logged?Least privilege, screen-pop only the active caller, audit every access
RRecords APICan you prove who changed an address or reset a PIN, and after what verification?Audit trail linking change, agent and verification result

3. Mistakes to avoid

  • Skipping the telephony side because “it’s the carrier’s problem”. Your IVR still decides what a caller may do.
  • Recording everything, always. Recordings are your largest store of personal data and, if you take card payments, may put you in scope of payment-card rules.
  • Trusting the phone number to identify a customer.
  • Drawing the agent as part of “the system” only. Agents are insiders: model their access and log it.
  • Forgetting the speech and code vendors. Audio and personal data go to them; they belong outside a trust boundary.

Reviewing any model

  • Does every process, store and external have at least one flow in and one flow out?
  • Does every arrow that crosses a boundary appear to cross it on the picture?
  • Can a stranger point at any arrow and be told what it carries and how it is protected?
  • Are the assumptions written down, and has someone checked at least the three most important?
  • Has every high-priority threat got an owner, a state and a justification?
  • Will someone update this when the architecture changes? Put it in the definition of done.

For management, produce the executive summary (Report → Download report…, or --format exec) and pick a clear font such as Verdana. See Reports and fonts.
