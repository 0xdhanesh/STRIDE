What is STRIDE, and why it matters

An introduction for developers, IT and operations, security engineers and managers: what STRIDE is, what a threat model is, why teams do it, and what it means for your role.

In one minute

STRIDE is a checklist for finding security problems in a design before the software is built (or while it is changed). It names six kinds of attack, one per letter, and you ask of every part of your system: “could this happen here?” It was created at Microsoft in the late 1990s (Loren Kohnfelder and Praerit Garg) and is now one of the most widely used threat-modeling methods.

The process is: draw how the system works, ask the six questions at every place information moves or is stored, decide what to do about each answer, and write it down. This tool automates the asking and the bookkeeping so people can spend their time on the deciding.

What a threat model is

A threat model answers four questions:

  1. What are we building? A simple diagram of the parts and the information flowing between them.
  2. What can go wrong? The six STRIDE questions, applied to each part and flow.
  3. What are we going to do about it? Fix it, reduce it, accept it knowingly, or hand it to someone else (for example a vendor).
  4. Did we do a good job? Review it, and revisit when the design changes.

It is a living document, not a one-off report. Small and honest beats big and abandoned.

The six STRIDE threats

EElevation of privilegeGetting more power than intendedAuthorizationA normal user reaching an admin function; code execution through unsafe inputServer-side authorization checks, sandboxing, least privilege

A quick way to remember it: S, T, R are about who did what and whether we can trust it; I, D are about data and service being there for the right people; E is about how far an attacker can get.

Why it matters

  • Cheaper. A design flaw found on a whiteboard costs a conversation. The same flaw found in production costs an incident, a fix, a release and sometimes a notification to customers.
  • It finds what scanners cannot. Scanners find bugs in code that exists. A threat model finds missing controls: the service that trusts any caller, the queue nobody authenticates, the recording that keeps card numbers.
  • One shared language. Developers, operations, security and managers can point at the same diagram and the same six words.
  • Focus. Not everything is equally risky. The model shows where data crosses trust boundaries, which is where attackers operate, so limited review time goes there first.
  • Evidence. Customers, auditors and regulators increasingly ask for one. A maintained model with decisions and reasons is that evidence.
  • Fewer surprises later. Third-party dependencies, new integrations and new data types get a deliberate look instead of an accidental one.

What it means for your role

Developers

You know how the system really works, so you are the best person to draw it. Use the model to:

  • Decide where input must be validated and where authorization must be checked.
  • Turn a threat into a concrete task or test (“every endpoint rejects a user without the role”).
  • Attach file:line evidence so findings point at code.
  • Update it in the same pull request that changes the architecture.

IT and operations

You own the network, the platform and the secrets. Use the model to:

  • Confirm that trust boundaries match reality (network segments, VPCs, accounts).
  • Check logging, monitoring and backups against the Repudiation and Denial-of-service threats.
  • Find where credentials and keys travel and who can read them.
  • Plan capacity and rate limits where flows are exposed to the internet.

Security engineers

You review many systems. Use the model to:

  • Review a design in minutes instead of reading code for days.
  • Rank findings: high-signal first, generic ones for architectural review.
  • Spot patterns that repeat across services and fix them once.
  • Keep a record of decisions, accepted risks and their reasons.

Product and management

You decide how much risk is acceptable. Use the model to:

  • Read the executive summary: status, headline numbers, the risks that matter most.
  • Ask for an owner and a date for each high-priority risk.
  • Make accept/fix decisions knowingly and have them recorded.

When to do it

  • Before building a new system or a big feature, when changes are cheap.
  • When the architecture changes: a new integration, a new data type, a move to the cloud, a new vendor.
  • After an incident or a penetration test, to see what the model missed.
  • On a schedule for important systems, because systems drift.

A first pass of a typical service takes an hour or two with the people who know it. The worked examples show what the diagram should look like for common systems.

What STRIDE does not do

  • It does not find code bugs. It tells you where to look and what to demand; it does not read your source for injection flaws.
  • It does not rate business impact for you. Priority here is a starting guess. People who know the business should set it.
  • It is only as good as the diagram. A missing flow means missing threats. Review the diagram with someone who did not draw it.
  • Generated threats are prompts, not verdicts. Some will not apply; some real threats will not be generated. Expert judgment stays in the loop.
  • It is not a one-time certificate. A model that is not kept current gives false comfort.

Words you will hear

TermMeaning
Data flow diagram (DFD)The picture: processes, external interactors, data stores, data flows and trust boundaries.
Trust boundaryA line where the level of trust changes, such as internet to internal network.
Attack surfaceEvery place an attacker can reach or influence: endpoints, inputs, file uploads, integrations.
MitigationA control that reduces a threat: validation, encryption, authorization check, rate limit.
Residual riskWhat is left after mitigation. It is accepted explicitly by someone with the authority to do so.
TemplateThe set of element types and threat rules the tool applies. The default is STRIDE Core; Microsoft’s .tb7 templates can be imported.
High signalA threat backed by concrete evidence such as a dangerous code path or sensitive data, as opposed to a generic architectural prompt.
