How to use STRIDE Threat Modeler

A practical guide for everyone who uses the tool: what each part of the screen and each building block means, how to draw a diagram, how threats are generated and how to work through them, and how to produce reports.

Start in two minutes

  1. Open the example. Choose File → Open example model. It is a small online shop, already drawn, with its threats generated.
  2. Look at the picture. Boxes and ovals are parts of the system, arrows are information moving between them, red dashed lines are trust boundaries.
  3. Open the Analyze view (top right). The threat list appears at the bottom, best findings first.
  4. Open a threat. Read what could go wrong, where, and the suggested mitigation. Set its state and add a justification.
  5. Start your own with File → New model, then follow “Drawing a diagram” below. New to threat modeling? Follow the learning path.
Everything runs in your browser. Nothing is uploaded. Your work is autosaved in this browser; use File → Save to keep a file.

The screen

AreaWhat it does

Design is for drawing and editing. Analyze is look-only: the tool bar is hidden and you can only pan and zoom, so you can study threats without moving anything by accident.

What each building block means

A diagram in this tool is a data flow diagram: who and what is involved, and how information moves between them.

BlockDrawn asMeaningExamples
ProcessOvalCode that runs and handles data. It receives input, does something and sends output.Web application, API, background worker, mobile app, IVR platform
External interactorRectangleA person or system outside your control that talks to yours. You cannot fix it, only defend against it.Customer, payment provider, partner API, phone carrier
Data storeTwo horizontal linesAnything that keeps data at rest.SQL database, file share, object storage, queue, cache, log files
Data flowArrowInformation moving from one element to another. Direction matters: draw one arrow per direction if both ways carry data.HTTPS request, SQL query, message on a queue, file upload
Trust boundaryRed dashed box or lineWhere the level of trust changes: who controls what is on each side. Threats are generated mainly where a flow crosses one.Internet ↔ your network, user device ↔ server, app ↔ database tier, your system ↔ a vendor
AnnotationFaint note boxA comment for readers. It never produces threats.Assumptions, “payments handled by provider”

Each stencil has a type (for example Web Service or SQL Database). The type matters: it carries properties such as “implements authentication”, and the threat rules read those properties. Pick the most specific type you can, and fill in the properties in the right-hand panel.

Drawing a diagram

  1. Place elements. Press P (process), E (external), D (data store), click the canvas, then type a name. Names appear in the generated threats, so use real names (“Orders API”, not “Service 2”).
  2. Connect them. Press F and drag from the source element to the target. The arrow snaps to both ends. Name it after what it carries (“Card payment”, “Order JSON”).
  3. Set types and properties. Select an element, choose its Type, and answer its properties. Answer honestly, “unknown” is better than a guess.
  4. Draw trust boundaries (next section).
  5. Check the Messages tab. It tells you about unconnected flows, missing boundaries and other gaps.

Handy: double-click a name to rename, drag corners to resize, drag the small circle on a selected arrow to bend it, hold Alt while dragging to duplicate, and double-click empty canvas to drop a note.

Trust boundaries

A trust boundary separates things that trust each other differently. Draw one wherever control, network, identity or privilege changes.

  • Box boundary (B): drag a rectangle around the elements that live together, for example “Internal network”. Any flow that goes in or out crosses it.
  • Arc boundary (L): drag a line across the flows that change trust, for example between a user device and the internet.
Crossing is geometric: a flow crosses a boundary if the drawn arrow actually cuts the boundary line. If an expected threat is missing, check that the arrow really crosses the boundary.

How threats are generated

Threats appear automatically a moment after you change the diagram (switch it off with Generate threats automatically in the threat model panel). For every data flow the tool looks at the source, the target, the flow type, their properties and which boundaries the flow crosses, then applies the rules of the template (default: STRIDE Core). Each match becomes a threat in one of the six STRIDE categories: Spoofing, Tampering, Repudiation, Information disclosure, Denial of service, Elevation of privilege.

So more detail gives better threats: connect every element, name every flow, set types and properties, and draw the boundaries.

High-signal threats

A big model can produce many generic threats. Each threat is scored; the High signal ones are backed by something concrete: source-code evidence, a dangerous call such as running a shell command, a weak control, or sensitive data. The High-signal view in the threat list shows only those, best first. Similar threats across many flows are collapsed into one with “Related flows: N”.

Working through threats

Open a threat from the list. For each one decide:

StateUse when
Not StartedNobody has looked at it yet (all new threats start here).
Needs InvestigationIt may be real; someone has to find out.
Mitigation ImplementedA control already exists or has been built. Say which one in the justification.
Not ApplicableIt cannot happen here. Write why.

Set a priority (High / Medium / Low) and write a justification. Your decisions are kept when threats regenerate. You can edit a threat’s title, description and mitigation, and use Add threat on a flow for something the rules did not find. Threats whose flow was deleted are shown as “no longer present” so your triage is never silently lost.

Colours, groups and focus mode

  • Line colours. Every element gets its own colour and all arrows leaving it use that colour, so arrows entering an element are told apart by where they come from. Select an element to change its Egress colour, or select one arrow to change just that Line colour. Reset returns to the default.
  • Clean routing. Arrows leaving an element share one exit point and fan out; each arrow entering an element gets its own entry point; arrows from different elements avoid running over each other.
  • Groups. Select several elements and press G (or Group in the panel). They now select and move as one. Shift+G ungroups. Groups show a faint dashed outline.
  • Focus mode. Ctrl/⌘+. hides every menu and panel so only the diagram remains; Esc brings them back. Press H for hand mode to pan around, and / to search stencils.

Reports and fonts

Open the Report menu and choose Download report… to pick the report type and the font, then Open in new tab or Download.

ReportForWhat is in it
Executive summarySenior management, sponsors, auditors who want the answerOne page of large, plain-language text: overall status, four headline numbers, the system picture, the five risks that matter most with a recommended action, and suggested next steps. No rule names, file paths or per-flow detail.
Technical reportEngineers and security reviewersExecutive summary, high-signal findings table with evidence, every diagram, every threat grouped by interaction, validation messages.
Markdown summaryPull requests, chat, agentsThe same stakeholder-first content as plain text.
Threat list (CSV)Spreadsheets and trackersOne row per threat, with spreadsheet-formula protection.
Diagram (SVG)Slides and documentsThe current diagram as a vector image.

Fonts. HTML reports can use any font that is installed on the computer that opens them: System default, Arial, Verdana (very clear, wide letters), Tahoma, Trebuchet MS, Calibri, Georgia, Times New Roman, Monospace, or type the name of any other installed font. The report uses your choice for all text including the diagram labels. Open the report on a machine without that font and the browser falls back to a default. Use the browser’s print dialog to save a report as PDF.

Saving, opening, templates

  • Save / Open (Ctrl/⌘+S, Ctrl/⌘+O) work with a .stride.json file. The model is also autosaved in this browser, but a saved file is the only copy you control.
  • Templates define the element types and the threat rules. Import a Microsoft Threat Modeling Tool template (.tb7) from File → Import template, or open Template & rules… to read and edit the rules. Threats are regenerated and your triage is kept.
  • Multiple diagrams. Use the + next to the tabs. Double-click a tab to rename it.

Building models from code (CLI and MCP)

The same engine runs without the browser, which is useful for CI and for AI agents that read a repository.

stride sync threatmodel/model.json threatmodel/spec.json   # build or update a model from a spec
stride report model.json --format exec --font verdana -o summary.html   # executive report
stride report model.json -o report.html                    # technical report
stride mcp                                                  # Model Context Protocol server

A spec lists trust zones, elements and flows; sync lays the diagram out so every flow crosses exactly the right boundaries. See the worked examples for four complete specs you can run as they are.

If something looks wrong

You seeTry
No threats appearConnect elements with data flows (F) and check Generate threats automatically is on. A diagram with no flows has nothing to analyse.
A boundary-related threat is missingMake sure a flow arrow truly crosses the boundary line, and that the right elements are inside the box.
Messages tab shows warningsEach message names the element. The common ones: unconnected flow, flow between two external interactors (usually out of scope), no trust boundary.
The tool bar is missingYou are in Analyze view or focus mode. Switch to Design, or press Esc.
The stencil pane is hiddenUse the first button in the top bar, or press / to search without it.
Autosave warningThe browser blocked storage. Save to a file.
