Learn threat modeling from scratch

A step-by-step path from “what is this?” to modeling a real system: reading order, a guided tutorial you build in the app, a ten-question self-check, a glossary and a reading list.

The learning path

Learning threat modeling is mostly doing it on real examples and getting feedback. Read a little, then practice. This path takes about two working days spread over a week or two, and ends with a real model of your own system.

StepDo thisTimeYou are done when you can…
1. UnderstandRead What is STRIDE20 minexplain the six threats to a colleague with one example each
2. Learn the toolRead How to use it and open the example model30 minname the five building blocks and say what a trust boundary is
3. Build one with guidanceThe guided tutorial below45 mindraw a small system, read its threats and triage three of them
4. Study a full exampleWorked examples: start with the web app30 minpoint out where each boundary goes and why
5. Practice, then comparePractice scenarios: try two before opening the answers2 hoursfind most of the model answer’s threats and a few it missed
6. Think like an attackerThinking like an attacker, and deciding what to do45 minrate a threat and choose fix, avoid, transfer or accept with a reason
7. Check yourselfThe quiz below15 minanswer at least 8 of 10 before looking
8. Do it for realModel one real system with a teammate who knows it2 hourshand a management summary to a decision-maker
9. Keep it aliveUpdate the model in the same change that alters the designongoingshow when each assumption was last checked
Learning alone? Do step 8 with someone who did not draw the diagram. A second person finds the missing arrows within minutes, and that is the fastest way to improve.

Guided tutorial: cinema booking

The system: customers pick seats and pay for cinema tickets on a website. The site keeps bookings in a database and takes payment through an outside payment provider. Small enough to finish in 45 minutes, real enough to show every idea.

Before you start, open the app and choose File → New model. Do not open the answer yet.

Part 1. Draw it

  1. Who is outside? Press E, click the canvas, type Customer and press Enter. In the right panel set Type to Human User. Press E again and add Payment provider with type External Web Service. Why external? You do not control either of them.
  2. What code runs? Press P, place Booking web app, set type Web Application.
  3. Where is data kept? Press D, place Bookings DB, set type SQL Database.
  4. How does information move? Press F and drag from one element to another. Draw six flows, one per direction, and name each one:
    Customer → Booking web app: Seat selection and details
    Booking web app → Customer: Booking confirmation
    Booking web app → Bookings DB: Booking reads and writes
    Bookings DB → Booking web app: Booking data
    Booking web app → Payment provider: Card payment request
    Payment provider → Booking web app: Payment result
  5. Where does trust change? Press B and drag a box around the web app and the database. Double-click its label and call it Our systems. Customer and payment provider stay outside: you cannot control them.
Check: what should the picture look like?

Two elements outside the box (Customer, Payment provider), two inside (Booking web app, Bookings DB), six arrows, and every arrow to or from an outside element crosses the box. The arrows between the web app and the database do not cross it.

Compare with the reference: download cinema-booking.json and in the app choose File → Open…, which accepts it directly and builds the diagram for you. Yours does not have to look identical; the elements, flows and boundary should match.

Part 2. Read the threats

  1. Check the Messages tab at the bottom: it should have no errors. Fix anything it reports.
  2. Open the Analyze view (top right). With these types you should see roughly 30 threats (the reference produces 29). If you see none, check that the flows really connect to the elements.
  3. Find a Spoofing threat on Seat selection and details. In your own words: who could pretend to be whom, and what would they gain?
  4. Find a Tampering threat on Card payment request. What could an attacker change between the app and the provider, and what stops them?
  5. Find an Information disclosure threat on Bookings DB. What is in there that would hurt if it leaked?

Part 3. Decide

  1. For each of the three threats set a state (for example Needs Investigation), a priority and a justification that names a specific control: “Stripe Checkout hosts the card form, so card numbers never reach us” beats “handled”.
  2. Add a threat the tool did not find. Think about booking: two customers choose the last seat at the same moment. That is Tampering with the booking data through a race condition. Select the flow Seat selection and details and use Add threat in the right panel. Write the title, description and a mitigation (for example a database uniqueness constraint on seat and showing).
  3. Set the Name, Owner and Assumptions in the model details (select nothing to see them). Write down one assumption you are relying on.

Part 4. Report it

  1. Choose Report → Download report…, pick Executive summary and a clear font such as Verdana, then Open in new tab.
  2. Read it as the owner of the business would. Is the status clear? Would they know what you are asking them to do?
  3. Now open the Technical report and compare what changed: the evidence, interactions and every threat appear there.

Part 5. Stretch

  • Add a refund flow and an email confirmation flow. What new threats appear? Who is the new outside party?
  • Add an admin who can cancel bookings. Where does the admin connect, and what boundary do they cross?
  • Press G with several elements selected to group them, change a line colour, and try focus mode (Ctrl/⌘+.).
What most people forget in this tutorial
  • The reverse flows (confirmation, query results, payment result). Data leaves on those too.
  • The admin and support staff: insiders are a threat source and an access path.
  • A log or analytics store, which often holds names and emails.
  • The email that confirms the booking: an unauthenticated channel with personal data in it.
  • Seat holds that expire: a denial-of-service lever (someone reserves every seat and never pays).

Check yourself: 10 questions

Answer in your head or on paper, then open the answer.

  1. A customer says “I never approved that refund” and nothing in the logs can prove otherwise. Which STRIDE threat is this?
    AnswerRepudiation. There is no reliable record tying the action to a person. Fix: audit logs of who did what and when, protected from editing.
  2. An attacker changes price=100 to price=1 in a request and the server accepts it.
    AnswerTampering. The server trusted data it should have computed itself. Fix: take prices from the server, never from the request.
  3. Changing /invoice/1001 to /invoice/1002 shows someone else’s invoice.
    AnswerInformation disclosure, caused by a missing authorization check (which is also the root of Elevation of privilege). Fix: check on the server that the invoice belongs to the caller.
  4. One user repeatedly uploads a 10 GB file and the site slows to a crawl for everyone.
    AnswerDenial of service. Fix: size limits, quotas, rate limits, processing in a separate queue.
  5. A stolen session cookie lets someone act as another user.
    AnswerSpoofing. Fix: short-lived sessions, secure cookie flags, re-authentication for sensitive actions, session revocation.
  6. An ordinary user calls an admin-only URL and it works.
    AnswerElevation of privilege. Fix: deny-by-default authorization on the server for every function, with a test per role.
  7. Is a message queue a process, an external interactor or a data store?
    AnswerData store. It holds data at rest, even briefly, so it needs access control, retention rules and monitoring like any store.
  8. Your app calls a third-party SaaS. External interactor or process?
    AnswerExternal interactor. You do not control its code or its security. Put it on the far side of a trust boundary and defend what you send and what you accept back.
  9. You only drew arrows from the user to the server. What did you miss?
    AnswerThe reverse flows. Responses carry data out. Draw one arrow per direction, named after what it carries.
  10. A threat is marked Not Applicable with the justification “handled”. What is wrong with that?
    AnswerIt names no control. A useful justification says which control, where it is enforced and ideally how it is tested, so a reviewer can verify it: “Server-side check in authz.py; covered by test test_roles.”

Glossary

TermMeaning
AssetSomething worth protecting: customer data, money, availability, reputation, a signing key.
ThreatSomething bad that could happen to an asset. “A stranger could read other users’ invoices.”
VulnerabilityA weakness that lets a threat happen. “The invoice endpoint does not check ownership.”
Threat actorWhoever or whatever causes a threat: an outsider, a customer, an insider, a compromised partner.
Attack surfaceEverything an attacker can reach or influence: endpoints, inputs, files, integrations, people.
Entry pointA specific place where data or control enters the system: a URL, a queue, an upload, a phone number.
Data flow diagram (DFD)The picture of processes, external interactors, data stores, data flows and trust boundaries.
Trust boundaryA line across which the level of trust changes, for example internet to internal network.
External interactorA person or system outside your control that exchanges data with yours.
AuthenticationProving who you are.
AuthorizationDeciding what an authenticated identity may do. Most serious web flaws are missing authorization.
Least privilegeGiving each person and component only the access it needs.
Defence in depthSeveral independent controls, so one failure is not the end.
MitigationA control that reduces a threat.
Residual riskThe risk that remains after mitigation, accepted knowingly by someone with authority.
Abuse caseA use case written from the attacker’s side: “As an attacker I want to reuse an old reset link.”
AssumptionSomething you rely on but have not verified. Write them down; check the important ones.
STRIDESpoofing, Tampering, Repudiation, Information disclosure, Denial of service, Elevation of privilege.
TemplateThe element types and threat rules a tool applies. This tool defaults to STRIDE Core.

Where to go next

This site teaches the method and the tool. For depth, these are widely used and worth your time (find the current editions and pages with a search):

  • Adam Shostack, Threat Modeling: Designing for Security (Wiley). The standard book on STRIDE and data flow diagrams, with exercises.
  • Izar Tarandach and Matthew Coles, Threat Modeling: A Practical Guide for Development Teams (O’Reilly). Aimed at teams who build and ship continuously.
  • The Threat Modeling Manifesto (threatmodelingmanifesto.org). A short statement of values and principles, written by practitioners.
  • OWASP (owasp.org): the Threat Modeling Cheat Sheet and Threat Modeling Process pages, and the Top 10 lists for common weaknesses to look for.
  • Microsoft’s threat modeling documentation and the Microsoft Threat Modeling Tool, whose templates this tool can import.
  • MITRE ATT&CK and CAPEC: catalogues of real attacker techniques and attack patterns, useful for “what could go wrong” brainstorming.
  • LINDDUN (linddun.org): a sister method for privacy threats, for when personal data is the main concern.
  • Kohnfelder and Garg, “The threats to our products” (Microsoft, 1999): the original STRIDE write-up, if you like origins.
