Practice scenarios

Four small, realistic features that systems often get wrong. Draw each one, find the threats, then compare with a model answer and a runnable spec.

How to practice

Each scenario is a small feature that real systems get wrong. Spend 20 to 30 minutes on each, before opening the model answer:

  1. Draw the diagram in the app (File → New model): elements, one arrow per direction, boundaries.
  2. Read the generated threats, then write down at least six threats of your own covering as many STRIDE letters as you can. Add the ones the tool missed with Add threat.
  3. Pick the two that worry you most and say how you would fix them, specifically.
  4. Only now open the model answer. Score yourself: how many did you find? Which did you miss, and why? Add the missing ones to your model.
The answers are written as one reasonable model, not the only one. If you found a good threat that is not listed, that is a win. Order is not important; reasons are.

1. Password reset

A user who forgot their password asks for a reset. The service creates a one-time token, stores a hash of it, and emails a link through an email provider. The user clicks the link and sets a new password.

Your tasks

  1. Draw the diagram. Which elements are outside your control?
  2. Where is the weakest link in the chain: which step relies on something you do not own?
  3. Write threats for at least four STRIDE letters.
  4. What should be logged, and what must never be logged?
Model answer (try it first!)

Elements, flows and boundaries

Trust boundaries: Our systems around the reset page, account service and accounts database. The user and the email provider are outside. Email is an untrusted channel that you do not control.

ElementTypeWhy
UserHuman User (external)Anyone can request a reset for any address
Reset pageWeb ApplicationPublic entry point
Account serviceWeb ServiceCreates and checks tokens
Accounts DBSQL DatabaseHolds password hashes and token hashes
Email providerExternal Web ServiceDelivers the link; outside your control
FlowCarries
User → Reset pageReset request with email address; later the link click and new password
Reset page → Account serviceCreate reset token; token and new password
Account service → Accounts DBStore token hash; update password hash
Account service → Email providerReset email with link

Threats to find

STRIDEWhereWhat could go wrongFix
SLink and tokenAttacker guesses or reuses a reset token and takes over the accountLong random single-use token, short expiry, stored only as a hash
SEmail channelAttacker with access to the victim’s mailbox resets the password silentlyNotify other channels, require extra verification for sensitive accounts, cool-down
TReset email with linkLink is built from the request’s Host header, so the email points to the attacker’s siteBuild links from fixed configuration, never from request headers
IReset requestDifferent responses reveal which emails have accounts (enumeration)Same message and timing whether or not the account exists
ILink clickToken in the URL leaks through logs, browser history and Referer headersExchange the token at once, no-referrer policy, never log query strings
RWhole flowNo record of who requested or used a reset, so abuse cannot be investigatedAudit events with time, address and result; alert on bursts
DReset requestAttacker floods one address with reset emails, or exhausts the email quotaRate limits per account and per source, captcha after a few tries
EUpdate passwordOld sessions stay valid after reset, or reset bypasses multi-factor sign-inRevoke sessions on reset; keep MFA requirements

What learners usually miss

  • That email is not secure. Anyone who can read the mailbox can use the link.
  • Tokens stored in plaintext in the database: a read-only leak becomes account takeover.
  • The timing side of enumeration, not only the message text.

Discussion: Is “anyone with the user’s mailbox” inside or outside your threat model? Write down the decision either way.

2. Payment webhook receiver

A payment provider calls a public webhook endpoint when a payment succeeds or fails. The endpoint puts verified events on a queue; a worker reads them and updates order status in the orders database.

Your tasks

  1. Draw it. Which element is exposed to the internet, and who can call it?
  2. What would an attacker send to this endpoint, and what would they hope to achieve?
  3. Find at least one threat for each of S, T, D and E.
  4. What can go wrong inside the system, after the endpoint?
Model answer (try it first!)

Elements, flows and boundaries

Trust boundaries: Our systems around the endpoint, queue, worker and database. The provider is outside. The endpoint is the part of your system that faces the internet.

ElementTypeWhy
Payment providerExternal Web ServiceSends events; you trust it only as far as the signature proves
Webhook endpointWeb ServicePublic, unauthenticated by session, authenticated by signature
Event queueCache (data store)Holds events until processed
Order workerWin32 ServiceApplies events to orders
Orders DBSQL DatabaseOrder status
FlowCarries
Payment provider → Webhook endpointSigned payment events
Webhook endpoint → Payment providerAcknowledgement
Webhook endpoint → Event queueVerified events
Event queue → Order workerEvents to process
Order worker → Orders DBOrder status updates

Threats to find

STRIDEWhereWhat could go wrongFix
SSigned payment eventsAnyone posts a fake “payment succeeded” and gets goods for freeVerify the signature over the raw body with the shared secret; reject anything unsigned
TSigned payment eventsA genuine old event is replayed (for example a refund or a success for another order)Reject stale timestamps and de-duplicate by event id
TEvents to processFields are trusted without checking amount and order against your own recordsValidate against the order, or re-fetch the event from the provider’s API
IAcknowledgementVerbose errors or logged full payloads expose personal dataMinimal responses, redact logs
DWebhook endpointFlooding the endpoint, or one malformed “poison” event that crashes the worker on every retryRate limit, acknowledge fast and process later, dead-letter queue and retry limits
EOrder status updatesThe worker’s database account can change everything, so a bug in event handling is a full compromiseLeast-privilege account that can only update order status
ROrder status updatesYou cannot tell which event caused which status changeStore the event id with every change; keep an append-only log
TEvent queueAnything inside the network can inject events directly, skipping signature checksAuthenticate queue producers; restrict who can publish

What learners usually miss

  • The queue is a data store with its own attackers: verification at the edge does not protect it.
  • Acknowledge only after the event is safely stored, or you lose events.
  • Secret rotation: what happens when the signing secret has to change?

Discussion: Should an unsigned request even reach your application code? Where is the earliest place to reject it?

3. Fitness mobile app

A phone app records workouts, keeps a local cache and syncs with a cloud API through a gateway. The API stores activity data and asks a push service to send reminders to the phone.

Your tasks

  1. Draw it. Which side of the main boundary do you control?
  2. Assume the phone is lost, rooted, or running a modified copy of your app. What breaks?
  3. Find the three most serious Information disclosure and Elevation of privilege threats.
  4. Where is the push service a risk to you?
Model answer (try it first!)

Elements, flows and boundaries

Trust boundaries: User device (you do not control it: treat everything on it as attacker-readable and attacker-modifiable) and Backend. The push service is outside.

ElementTypeWhy
Phone userHuman User (external)The legitimate user, or whoever holds the phone
Mobile appGeneric ProcessRuns on the device: not trustworthy to enforce rules
Local cacheDevice (data store)Cached activity and tokens on the phone
API gatewayWeb ServerBackend entry point
Fitness APIWeb ServiceBusiness logic and authorization
Activity DBNon Relational DatabaseHealth-related data
Push serviceExternal Web ServiceDelivers notifications through the phone vendor
FlowCarries
Phone user ↔ Mobile appTaps and sensor data
Mobile app ↔ Local cacheCached activity and tokens
Mobile app ↔ API gatewayAPI calls with token; responses
API gateway → Fitness APIForwarded calls
Fitness API → Activity DBReads and writes
Fitness API → Push service → Mobile appReminder requests and notifications

Threats to find

STRIDEWhereWhat could go wrongFix
SAPI calls with tokenA stolen or copied access token is used from another deviceShort-lived tokens, rotating refresh tokens, revoke on logout or loss
TAPI calls with tokenA proxy changes the user id or activity id in a requestServer-side checks on every request; never trust values that came from the app
EForwarded callsChanging an object id returns or edits another user’s data (broken object-level authorization)Ownership check in the API on every object access, with tests
ILocal cacheTokens and health data are readable on a lost, rooted or backed-up phoneOS secure storage, encrypt the local database, store the minimum, exclude from backups
IAPI responsesThe API returns more fields than the screen showsExplicit response shapes, no entire-record returns
IPush notificationsSensitive details appear on the lock screen or pass through the push vendorSend “you have an update”, fetch details after sign-in
DAPI calls with tokenBulk sync or reminder abuse overloads the API or spams a userPer-user and per-device rate limits, page-size caps
RAPI calls with tokenYou cannot tell the user from a thief using a stolen phoneDevice-bound sessions, audit trail with device id, user-visible session list with revoke

What learners usually miss

  • Secrets inside the app (API keys, signing keys): they can be extracted from the package.
  • Old app versions that are still allowed to call your API.
  • The transport on hostile networks: TLS everywhere, and a plan if you pin certificates.

Discussion: The golden rule of this scenario: anything checked only in the app is not checked.

4. File sharing by link

A file owner creates a share link with an expiry and permissions. Anyone with the link can open it; the web app asks the link service whether it is valid, then fetches the file from storage.

Your tasks

  1. Draw it. Who is the “recipient”, and what do you actually know about them?
  2. List three ways a link could reach someone it was not meant for.
  3. Can a recipient reach the file without going through the link service? How would you stop that?
  4. What should the owner be able to see afterwards?
Model answer (try it first!)

Elements, flows and boundaries

Trust boundaries: Our systems around the web app, link service, links database and file storage. Owner and recipient are outside; the recipient is anonymous.

ElementTypeWhy
File ownerHuman User (external)Authenticated, creates links
Link recipientHuman User (external)Anonymous: whoever holds the link
Web appWeb ApplicationEntry point for both roles
Link serviceWeb ServiceCreates and validates links
Share links DBSQL DatabaseLink, expiry, permissions, target file
File storageCloud StorageThe files; must not be reachable directly
FlowCarries
File owner → Web app → Link serviceCreate link
Link service ↔ Share links DBStore and look up link, expiry, permissions
Link recipient → Web app → Link serviceOpen and validate link
Web app → File storageFetch file
Web app → Link recipientFile download

Threats to find

STRIDEWhereWhat could go wrongFix
IOpen linkShort or predictable links are guessed or enumeratedAt least 128 bits of randomness, rate limit validation, identical responses for missing and expired links
ILink and downloadA forwarded link, chat preview or Referer log exposes the file to more peopleExpiry, optional sign-in or passcode, revocation, no-referrer policy, per-link access log
IFetch fileStorage objects are public or signed URLs live for days, bypassing the link servicePrivate storage, short-lived signed URLs minted only after validation
TCreate linkPermissions or expiry are taken from request parameters the client can editServer derives permissions from its own stored record only
SOpen linkAnyone with the link is “the recipient”; you cannot tell who it really wasDecide knowingly: accept, or require sign-in for sensitive files
EValidate linkA link meant for one file grants access to a folder or sibling files (path tricks)Scope the link to one object id, normalise and check paths
DFetch fileRepeated downloads of huge files exhaust bandwidth and costRate limits, quotas, download caps per link
RFetch fileThe owner cannot see who opened or downloaded a fileAccess log with time and source per link, visible to the owner

What learners usually miss

  • Deleting the file must invalidate its links, and expired links must really stop working.
  • Serving user files from the main site’s domain can let a malicious file attack other users; use a separate download domain.
  • The decision that bearer links are weak authentication: write it down as an accepted risk or add a control.

Discussion: Is a share link a convenience feature or a security feature? Your answer sets how strong it needs to be.

After the answer

  • Add every threat you missed to your model with Add threat, so the practice leaves something behind.
  • Pick one scenario and explain it out loud to someone else in five minutes. Gaps show up immediately.
  • Change one thing in the scenario (add a login, add a vendor, add an admin) and see which threats appear or change.
  • Then try a system you work on. Start with its single most exposed entry point.
